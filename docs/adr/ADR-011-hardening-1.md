# ADR-011: Hardening, part 1 (shared rate limits, link role, audit gaps, "not allowed" page)

Status: accepted, Phase 9a. Supersedes the two deviations written in ADR-006 "As built".

- **Shared rate limits.** `public.rate_limit_hit()` (platform migration 0005) counts attempts per key in fixed windows with one atomic upsert, so all servers share one count and simultaneous requests are counted exactly. Keys are hashed before storage: no email address, address or token is kept. Used for sign-in (30 per address and 8 per account per 10 minutes) and for the odometer link (views per address; sends per address and per link). If the database cannot be reached the limiter falls back to a per-process count instead of failing open or locking everyone out. The function is revoked from PUBLIC, `anon` and `authenticated`: Supabase exposes functions in `public` through its API by default, which would let anyone use up other people's allowance.
- **The odometer link runs as a database role.** Migration 0011 creates `odometer_link` (no login, no inheritance). The link route switches to it with `SET LOCAL ROLE`; it has no table privileges, only EXECUTE on `link_submission_info` and `submit_odometer_via_link`, which are `SECURITY DEFINER` with a pinned `search_path`. The second function now also marks the link used, so the route never touches the links table. Tests check 20 forbidden statements (all denied), that the two functions still work, and that another workspace's schema is unreachable. Verified on the live database.
- **Limit that remains (honest):** `SET ROLE` is checked against the connection's login user, so code that could run arbitrary SQL inside the link context could switch back. The role guards against mistakes in the two small files that use it, which only run fixed, parameterised statements. A real wall would be a separate database login with its own connection string for the link route. Not done: it adds a second secret and a second pool. Revisit if the link code ever grows.
- **Audit gaps closed.** The review found four tables that changed without a trace: `attachments`, `reason_codes`, `roles`, `permissions`. They are now audited. `tests/audit-coverage.test.ts` fails for any tenant table that is neither audited nor excused with a written reason (excused: the log itself, migration bookkeeping, job card events which are their own history, notifications, reminder bookkeeping).
- **"Not allowed" page.** `ForbiddenError` carries the marker Next.js uses for `forbidden()`, with `experimental.authInterrupts` on and `app/forbidden.tsx`, so a page opened without permission shows a plain explanation instead of an error screen. Server actions still turn the same error into a message in the form.
- **Not in this part:** plan-limit enforcement, demo seed data, onboarding, an audit log viewer screen.
