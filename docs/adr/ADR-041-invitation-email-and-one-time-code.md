# ADR-041: Employees are added with an invitation; the link is emailed too; a WhatsApp code confirms it

Status: accepted, 2026-10-28. Amends ADR-025 and ADR-026 (invitations and the phone-only link).

## Decision
1. **An employee is only ever added together with an invitation, with every detail filled in.** The invite form on the Users page (the only way in) asks for the full name, employee number, department, phone number and role, and either an email or, for someone with no email, a sign-in name. `addEmployeeWithInvite` makes the employee record and the invitation in one transaction, so a record with no way to sign in cannot be left behind, and a refused invitation (plan limit, an open invitation) leaves no record. It needs both `admin.users` and `employee.manage`. The Employees page no longer has an add form; it edits what exists. Workshops are unchanged (the Vendors flow).
2. **The invitation link is also emailed** when the invitation has an email (`src/lib/email/invitation.ts`), so "Send invitation" does what it says. The WhatsApp and text buttons stay. The screen says whether the email went; a mail problem never undoes the invitation. "Send a new link" emails the new link too. This replaces ADR-026's "nowhere else".
3. **A one-time code confirms the link** (`src/lib/admin/invite-otp.ts`). When WhatsApp sending is set up and the invitation has a phone number, the invitation page asks for a 6-digit code before it makes the account. "Send me a code" sends it on WhatsApp to the number the administrator typed for the employee; the administrator never sees it. Only a hash is stored; it runs out after 10 minutes; five wrong tries end it; a new code at least 60 seconds apart, five per invitation, ten per connection per 10 minutes. A forwarded or stolen link is no use without the employee's WhatsApp. Not asked for on a password reset (the recovery code protects that) or when WhatsApp sending is not set up.
4. **WhatsApp sending is off until the owner sets it up** (`src/lib/whatsapp.ts`, Meta's WhatsApp Business Platform / Cloud API by plain REST, no library, using the owner's own WhatsApp Business account): `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN` (a permanent system-user token), `WHATSAPP_OTP_TEMPLATE` (the name of the approved authentication template that carries the code) and optionally `WHATSAPP_TEMPLATE_LANG` in Netlify. WhatsApp lets a business start a conversation only with an approved template, so the template is needed in production; without it the code goes as plain text, which only reaches people who messaged the business in the last 24 hours. No key, no code asked, invitations work as before. Each message costs money.
5. **The page that sends the message is open to anyone with a link** (CLAUDE.md rule 5, ADR-012): it only messages the number already on the invitation, never one a visitor supplies, and the answer says only the last four digits.
6. **Migration:** platform 0014 (`public.invitations` gains the code's hash, expiry, tries and sends).

## Not done
- The invitation link itself is still handed over by the administrator's own WhatsApp or text (ADR-026), plus the email. Sending the link from the server needs a second approved template.
- No SMS fallback if WhatsApp is not installed on the employee's phone.
- A person who is invited without an email and without a phone cannot exist (every invitation needs a number, ADR-026).
- The code protects the invitation link; accepting from the home page by a confirmed email is unchanged.
